# Approved parity exceptions

The corpus (`parity/corpus/`) is a **frozen M7 compatibility asset**: its expected results originate from the Python oracle (`python-1.0.0rc1`, commit `5c63ffc`) and must never be regenerated from Node. A difference between Node and the corpus is a Node defect unless it is listed here. Exceptions are approved by the human reviewer; the corpus data is not edited to accommodate them: replayers apply the exception rules below.

| ID | Scope | Rule | Basis |
|---|---|---|---|
| **PARITY-EXCEPTION-001** | GitHub provider spawn failure | Python 1.0.0rc1 can leak an uncaught OS/process exception (for example `PermissionError`) when `gh` exists but cannot be executed. Node 2.0.0 intentionally normalizes **every** failure to start the GitHub CLI (missing, not executable, permission denied, any spawn error) to the existing `provider-unavailable` failure class. Not a parity failure. Node regression tests added in M7.4 (`test/provider.test.ts`: missing binary, non-executable file, directory, bad shebang, unreadable directory). | Corrects behavior inconsistent with the approved M5 provider-failure contract. No corpus case exercises it. **Oracle evidence (M7.4):** a non-executable `gh` makes Python 1.0.0rc1 exit 1 with an uncaught `PermissionError: [Errno 13] Permission denied` traceback. |
| **PARITY-EXCEPTION-006** *(approved at the M7.4/M7.5 gate)* | Malformed GitHub provider response structure | A GitHub CLI response for the repository preflight that is JSON but not an object (e.g. a list) makes Python crash with `AttributeError: 'list' object has no attribute 'get'` (exit 1, traceback). Node 2.0.0 intentionally classifies this as `provider-failed`: the external provider returned a structurally invalid response, and leaking an implementation exception is not part of the approved CLI contract. Same rationale as 001: the provider contract is preserved, not Python implementation crashes. | Evidence: `fakegh` mode `repo_bad_json` variant with array output on the oracle; Node test `provider.test.ts` (EX-006 case). |
| **PARITY-EXCEPTION-002** | argparse-generated help/usage text (platform-runtime presentation) | The 12 corpus cases marked `text_parity: "argparse"` are exempt from byte parity of argparse's prose. Required instead: exit code **2** for usage errors (`0` for help), correct command/option recognition, the required command/flag names present in useful deterministic output, documented CLI behavior. No cloning of argparse punctuation, wrapping, capitalization or wording. **All application-owned diagnostics remain byte-exact.** | Human decision at the M7.1 gate. |
| **PARITY-EXCEPTION-003** | Version string | `sdlc --version` prints `sdlc 2.0.0-rc.1` (Python: `sdlc 1.0.0rc1`). | Approved target version (M7 plan §4). |
| **PARITY-EXCEPTION-004** *(approved)* | YAML parser diagnostic prose | Invalid YAML must keep being rejected with the same SDLC diagnostic classification (`bad-front-matter` / `bad-config`), exit behavior and the documented `invalid YAML: …` shape. The third-party parser's explanatory prose after that prefix does not need to match PyYAML. The Node layer still reproduces PyYAML's context line for common classes and every `invalid YAML value:` constructor message exactly (31 of 36 oracle error inputs identical; 5 differ in prose only). | Human decision at the M7.2 gate: parser-library-owned prose is not an SDLC behavioral contract (same rationale as 002). |
| **PARITY-EXCEPTION-005** *(approved)* | ASCII-only numeric IDs | SDLC identifiers use ASCII digits `0-9` (`BR-NNN`, `PR-001-R003`, …). Python's acceptance of other Unicode decimal characters through `\d` is accidental regex behavior and is not reproduced. TypeScript patterns use explicit `[0-9]` so the constraint is intentional and visible. | Human decision at the M7.2 gate. |
| **PARITY-EXCEPTION-007** *(approved: "clear error diagnostic", M7.6 differential)* | Project text file that is not valid UTF-8 | Python 1.0.0rc1 leaks an uncaught `UnicodeDecodeError` traceback (exit 1) in validate, status, list, references, update-map, … Node 2.0.0 decodes strictly and reports a clear `invalid-encoding` error: a document is one per-document error (reported by validate, skipped by list/status/references, never rewritten, publishing blocked); an unreadable config, ledger or map fails the command that needs it (exit 1, nothing written). No stack trace, file bytes never altered. A leading BOM and CRLF remain valid, as in Python. | Human decision at the M7.6 gate (Layer C differential run). Node tests: `test/invalid-encoding.test.ts`. |

**Documented, non-contract YAML compatibility limitations** (not exceptions to approve; unsupported unless they become reachable through an approved SDLC document behavior): `!!binary` and `!!set` raise an error in Node (Python constructs bytes/sets); a plain scalar folded across a literal U+2028/U+2029 keeps that character in PyYAML but folds to a space in Node.

## Dropped (dead / shadowed / unreachable) Python code

See `parity/DROPPED.md`. Rule (human decision): the Python code is a behavioral oracle, not a source oracle; code proven to have no reachable behavior is not ported. Each omission is recorded with the Python symbol/path, why it is dead, and the evidence. Anything whose reachability is uncertain is ported until proven otherwise.
