# create-stories

Turns product requirements (or a described need) into one or more **Draft** Story documents in `Stories/`, each with observable acceptance criteria and correct traceability. Audience: implementers and product reviewers.

Method: `../../shared/interview.md` (read it). Sections and rules: `references/section-catalog.md`. Questions to draw from: `references/discovery-questions.md`. Layout to write: `references/template.md`. Conventions: `../../shared/document-conventions.md`, `map-conventions.md`, `reference-conventions.md`. CLI: `sdlc` (`../../shared/cli-contract.md`); if it fails with `command not found: sdlc`, tell the user to install the library and stop. All commands run from the project root.

## Workflow

1. **Initialize and discover.** Run `sdlc init` (safe to repeat). Read the root `map.md` and `Stories/map.md`; run `sdlc list`.
2. **Find sources.** Ask which PRD or documents the Stories come from, or look at `sdlc list --category PR`. Read the source documents in full. Collect the **actual requirement IDs** declared there (lines like `- **PR-001-R003** — …`; confirm with `sdlc references <ID>`). No source at all is fine: those Stories are **standalone** (`covers: []`). Never invent requirement IDs or create a PRD only to have something to link.
3. **Classify the request:** *new* Stories, *revise* an existing Story, *split/extend*, or *summarize*. Ask if unclear.
4. **Propose a breakdown** (from the source, as a suggestion): candidate Story titles with the requirement IDs each would cover. Keep scopes distinct and sizes sensible. Agree the breakdown with the user.
5. **Check overlap before creating each new Story.** Run `sdlc find-overlaps --category US --title "<proposed title>" --purpose "<one sentence>" --covers <requirement IDs>`. (`--covers` here is a search hint; a Story's own front matter `covers` holds requirement IDs only.) If candidates come back: Present the candidates **exactly as the CLI returned them**: for each, its ID, title, `level`, `score` and every `reason`, copied from the command output (`--json` is easiest). Do not paraphrase, round, reorder, summarize or invent any ID, score or reason; if the command returns no candidates, say so. Then ask the user to choose **revise/extend the existing Story** or **create a new one**. Never merge or duplicate silently. Do this **before** `allocate-id`.
   **Contextual overlap review (after the CLI check, before `allocate-id`).** The CLI score is lexical and can miss a document about the same concern in different words, so also review context yourself: run `sdlc list --category US`, read the titles and purposes and the summaries in `Stories/map.md`, and open any document that looks close. For Stories also note which requirement IDs existing Stories already cover (`sdlc references <requirement ID>`). Present anything you judge to be a conceptual overlap **separately**, under the heading **Conceptual overlaps (my judgement, not CLI-scored)**: the document ID, its title, and one sentence saying why, quoting its title or purpose. Never attach a score, percentage or level to these, never merge them into the CLI list, and never invent a similarity value; if you see none, say "No conceptual overlaps found." Do this even when the CLI returned no candidates. Whenever either kind of overlap exists, ask the human to choose **revise** the existing Story, **relate** (create a new Story that links the existing one under `### Related To`), or **create new** (independent). Do not allocate an ID until they choose; *revise* follows the revision workflow, *relate* and *create new* continue with a new document.
6. **Interview** per `shared/interview.md`: about 3–5 related questions per round, only what the source does not settle — business rules, edge cases, negative paths, observable acceptance. Adapt, skip answered questions, accept `Unknown`/`TBD`/`Not applicable`, offer options as suggestions. Do not invent rules or acceptance criteria the user or source did not provide; After every round, give the **mandatory recap** (`shared/interview.md`) before asking the next questions. an unknown outcome is **not** an acceptance criterion: never write it as a Given/When/Then line with `then TBD`. Put it under `### Unresolved Acceptance Behavior (TBD)` as a `- **TBD** — …` bullet that states the open question (not a made-up result) and list it in Open Questions. If the user identifies behavior missing from the PRD, suggest updating the PRD with `create-prd`; do not add requirements here.
7. **Draft and review.** Show the Stories (title, `covers`, acceptance criteria, edge cases) with **assumptions, TBDs and tradeoffs** listed; every covered requirement must be addressed by at least one criterion. Revise until the user says to write them. Do not write files before that.
8. **Write (new Stories).** For each: `sdlc allocate-id --category US --title "<title>"` → use the returned `id` and `path`. Fill `references/template.md`: `status: Draft`, `delivery_status: Not Started` (unless the user explicitly sets another valid state — never `Implemented`/`Verified`), `created`/`updated` = today from `date +%F`, `covers` = the specific existing requirement IDs (or `[]`), and **every owning document linked under `### Derived From`** with a valid relative link. Requirement IDs must exist; no document IDs in `covers`. If the user chose **relate** in the overlap review, link that Story under `### Related To`.
9. **Revise (existing Story).** Read it; show proposed material changes and get agreement; edit in place keeping ID and filename. Update `covers`/`Derived From` together. A material change (scope, acceptance criteria, `covers`, references) to an `Approved` Story sets document `status: In Review` and `updated` to today, and you **tell the user explicitly**. `delivery_status` is separate: the only automatic change is the R2 invalidation rule (`../../shared/technical-conventions.md` §3): if the Story is `In Progress`, `Implemented` or `Verified` and you materially change its acceptance criteria, scope or `covers`, set `delivery_status: Ready` and tell the user; otherwise never change it as a side effect. If a covered requirement was retired, follow the replacement in the retired-reference diagnostic (or ask the user) and update `covers`.
10. **Index and validate.** Run `sdlc update-map`, then `sdlc validate`. Report **errors, warnings and coverage notices separately**. A standalone Story produces a `story-no-coverage` **notice** (not an error; exit 0); say so, and do not "fix" it by inventing requirements. Uncovered PR requirements are notices too. Fix errors you caused and re-run. Do not claim success while errors remain.
11. **Report.** For each Story give the path, ID, `covers`, criteria count, TBDs; then the validate summary. Approval and any later `delivery_status` changes are the human's decisions.

## Rules

- Never set `status: Approved` on your own; only if the user explicitly states that they approve the document.
- Never set `delivery_status` to `In Progress`, `Implemented` or `Verified`, and never to `Ready` on your own (that is the human's declaration, recorded by `refine-stories`).
- Never invent requirement IDs, rules, acceptance criteria, dates or approvals.
- Never hand-calculate IDs, edit `.sdlc/ledger.md`, or edit the generated region of a `map.md`.
