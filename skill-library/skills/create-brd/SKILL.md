# create-brd

Turns a business idea into a **Draft** BRD in `BR/` through a short, adaptive interview, then keeps the project maps and validation clean. Audience: business stakeholders. The BRD says what the business needs and why, not how the product works.

Method: `../../shared/interview.md` (read it). Sections and rules: `references/section-catalog.md`. Questions to draw from: `references/discovery-questions.md`. Layout to write: `references/template.md`. Conventions: `../../shared/document-conventions.md`, `map-conventions.md`, `reference-conventions.md`. CLI: `python -m sdlc` (`../../shared/cli-contract.md`); if it fails with `No module named sdlc`, tell the user to install the library and stop. All commands below run from the project root.

## Workflow

1. **Initialize and discover.** Run `python -m sdlc init` (safe to repeat). Read the root `map.md`, `BR/map.md`, and run `python -m sdlc list`. Read any material the user pointed to, and existing BRs that may relate.
2. **Classify the request:** *new* BRD, *revise* an existing one, *extend* it with more requirements, or *summarize*. Ask if unclear.
3. **Check overlap before creating anything new.** Run `python -m sdlc find-overlaps --category BR --title "<proposed title>" --purpose "<one sentence>"`. If candidates come back: Present the candidates **exactly as the CLI returned them**: for each, its ID, title, `level`, `score` and every `reason`, copied from the command output (`--json` is easiest). Do not paraphrase, round, reorder, summarize or invent any ID, score or reason; if the command returns no candidates, say so. Then ask the user to choose **revise/extend the existing one** or **create a new one**. Never merge or duplicate silently. Only when there are no candidates, or the user chose *new*, continue with a new document. Do this **before** `allocate-id`.
   **Contextual overlap review (after the CLI check, before `allocate-id`).** The CLI score is lexical and can miss a document about the same concern in different words, so also review context yourself: run `python -m sdlc list --category BR`, read the titles and purposes and the summaries in `BR/map.md`, and open any document that looks close. Present anything you judge to be a conceptual overlap **separately**, under the heading **Conceptual overlaps (my judgement, not CLI-scored)**: the document ID, its title, and one sentence saying why, quoting its title or purpose. Never attach a score, percentage or level to these, never merge them into the CLI list, and never invent a similarity value; if you see none, say "No conceptual overlaps found." Do this even when the CLI returned no candidates. Whenever either kind of overlap exists, ask the human to choose **revise** the existing BRD, **relate** (create a new BRD that links the existing one under `### Related To`), or **create new** (independent). Do not allocate an ID until they choose; *revise* follows the revision workflow, *relate* and *create new* continue with a new document.
4. **Interview** per `shared/interview.md`: ask about 3–5 related questions at a time, problem and outcomes first; skip what is known; adapt; accept `Unknown`/`TBD`/`Not applicable`; offer options as suggestions. Do not invent stakeholders, numbers, targets or decisions. After every round, give the **mandatory recap** (`shared/interview.md`) before asking the next questions.
5. **Draft and review.** After the first useful round, show a substantive draft (real content from the answers, using the section catalog) with **assumptions, open questions/TBDs and material tradeoffs** listed. Revise until the user says to write it. Do not write files before that.
6. **Write (new document).**
   - `python -m sdlc allocate-id --category BR --title "<title>"` → use the returned `id` and `path`.
   - For every business requirement, `python -m sdlc allocate-id --requirement <BR-ID>` and use the returned ID. Allocate only requirements that will actually be written.
   - Fill `references/template.md` (layout and rules in the section catalog): `status: Draft`, `created`/`updated` = today's date from the shell (`date +%F`), `purpose` = one sentence. Remove sections that do not apply, keep the core ones. Unresolved unknowns stay visible (`TBD`, Open Questions).
   - If the user identified related documents, or chose **relate** in the overlap review, list them under `References` (`### Related To` for a related BRD) with valid relative links (see `reference-conventions.md`); otherwise leave `None identified.` Never create an upstream document to fill a link.
7. **Revise (existing document).** Read it fully. Show the proposed material changes and get agreement. Then edit in place: preserve unrelated authored content, keep the same document ID, filename and existing requirement IDs when wording changes. Added requirement → `allocate-id --requirement <BR-ID>`. Removed requirement → `python -m sdlc retire-id <BR-ID-Rnnn> [--replaced-by <ID>] --note "<why>"`, and either delete its line or mark its text *Retired*; then update every Story `covers` and reference to it (`python -m sdlc references <ID>` finds them) — ask the user how affected Stories should change. Moving a requirement to another document follows the reconciliation in `document-conventions.md`.
   - **Approved documents:** if the change is material (requirements, scope, objectives, success measures, references) and `status` is `Approved`, set `status: In Review`, set `updated` to today, and **tell the user explicitly** that approval was reset and why. Typo/formatting fixes are not material. Always update `updated` on any edit.
8. **Index and validate.** Run `python -m sdlc update-map`, then `python -m sdlc validate`. Report **errors, warnings and coverage notices separately**. Fix errors you caused (broken links, bad metadata) and re-run. Do not claim success while errors remain. Note that BRD requirements themselves produce no coverage notices in R1.
9. **Report.** Give the path, ID, status (`Draft` unless unchanged), list of requirement IDs, the remaining TBDs, and the validate summary. Point out that approval is the human's decision.

## Rules

- Never set `status: Approved` on your own. Only if the user explicitly states that they approve the document may it be recorded as Approved.
- Never invent business decisions, KPIs, dates, stakeholders or approvals. Unknown stays unknown.
- Never hand-calculate IDs, edit `.sdlc/ledger.md`, or edit the generated region of a `map.md`.
- One BRD must not depend on a PRD or design; do not add product or technical solution detail.
- Success Measures and requirements state only what the user established; an unresolved one is written as `TBD` (with a target only if the user gave one), never as an assertion.
